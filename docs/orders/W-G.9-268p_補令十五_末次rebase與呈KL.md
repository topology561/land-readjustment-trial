## §三　發單側之二自誤

### 三-1　`自誤 350`（責 ＝ **發單側**）

**形**：**將 git blob 之 `sha1` 標為 `sha256`。**
補令十四 `§五 (i)` 逐字載「`app.py` blob `sha256` … （`1d7d7c73…`）」——該值實為 **blob `sha1`**（`1d7d7c7324719f13e7d61473a55001170ef44d8e`）；其 `sha256` 為 `b74fd07c3c86a914…`。**值正確、標記誤**，即倉內既載之「二式並存·⛔ 混用」。
🔒 **CC 之二式並報、⛔ 改單、⛔ 鑄號、立為坑 `21`——處置正確，核可。**
**通則**：**凡出艙一雜湊，須同格具名其式（`git blob sha1`／`file sha256`／`tree sha1`），⛔ 以「sha」或錯式冠之。二式並存之受詞，一律二式並報。**

### 三-2　`自誤 351`（責 ＝ **發單側**·🔴 **差一步即成不實指控**）

**形**：**以本地追蹤 ref 判遠端態，而未執行<u>自己每一份單皆明令</u>之攔法（`ls-remote` 實查·⛔ 採信本地 ref）。**
發單側之 `git fetch` refspec 作 `refs/heads/*:refs/remotes/origin/*`（**未帶 `+`**）⇒ 側支之追蹤 ref 因非快轉而**被拒絕更新**，仍停於 `10d8202`；發單側據之一度判「側支 ＝ `10d8202`」，其義即 **CC 之 `--force-with-lease` 推送未落地**。實查 `ls-remote` ＝ `9f8d980`，**CC 之推確已落地**。
🔒 **僅因讀到 `fetch` 輸出之 `! [rejected] … (non-fast-forward)` 一列而當場攔下**；未讀該列即出艙者，即成對 CC 之**不實指控**。
🔒 **與 `347` 同族之再現**：`347` 之通則逐字為「⛔ 以『已讀過該交接註』代替『已執行其攔法』」；本則係**攔法為發單側自立**且**逐單重申**，仍未執行。**須逐字併記為 `347` 之再現**，⛔ 以新號掩之。
**通則（增訂）**
> **凡判遠端 ref 之態，一律 `git ls-remote` 實查；本地追蹤 ref ⛔ 得作證——其更新可因 refspec 未帶 `+`、或 `--prune` 未用而<u>靜默或半靜默地</u>不生效。**
> **且：凡出艙「他方之動作未落地」之判，須先自證己方之觀測管道有效；未自證者⛔ 出艙該判。**

## §四　🔴 快轉二度不成立 ⇒ 立準 ＋ 末次 rebase

### 四-1　所診

🔴 **成因與前次同一**：**rebase 做畢後又推物件至主線**。

### 四-2　立準（**爾後適用·硬**）

> **側支存在且待併線之期間，主線⛔ 前進——<u>零生產碼之 commit 亦然</u>，一律改落側支。**
> 🔒 **由**：側支終將快轉併入主線，零生產碼之物件落側支⛔ 生害，卻使「快轉」於全期間恆成立，整類「rebase 後主線又動」之問題隨之消滅。
> 🛑 **例外**：僅當該 commit **必須**先於併線生效（如解除一項阻塞側支本身之閘）方得推主線，且推畢**須即刻 rebase 側支並重驗**，⛔ 留待下一輪。

### 四-3　末次 rebase（**須為本批推向<u>任何</u> ref 之最後一個動作**）

側支 rebase 至主線 tip `7eaa485` 後以 `--force-with-lease`（具名舊值 `9f8d980`）重推。
