## 工項一　🔴→🎉 **活體攔截實測**（`W-G.9-237R` 所立之開窗必辦·**接線成立**）

### 一之 `a`　首跑 ⇒ 🔴 **未被攔**

發一則含 `⟨INTRO⟩` 之 `Bash` 命令（引號內·執行亦無害）⇒ **命令照常執行、`rc = 0`**
⇒ 依 `W-G.9-237R` 之明文「未被攔即**接線失敗**，須**停並回報**」⇒ **進入診斷**。

### 一之 `b`　🩸 **第一個真缺陷**：`stdin` 走平台預設編碼 ⇒ **誤攔一切含 CJK 之命令**

次一則命令（**含中文**、⛔ 含 `⟨INTRO⟩`）**竟被攔**，其 harness 訊息逐字（節錄）：

> `PreToolUse:Bash hook error: [python "…wg9237_heredoc_guard.py"]: … hook 事件 JSON 解析失敗 ⇒ 阻斷`

🔒 **⇒ 二事同時坐實**：① **hook <u>確已接線</u>**（其確在攔）；
② **guard 有真缺陷**——`sys.stdin.read()` 走**平台預設編碼**（本機 `cp950`），
命令含 CJK 時其 UTF-8 位元組以 `cp950` 解碼後**破壞 JSON 結構** ⇒ 落入「解析失敗 ⇒ 阻斷」
⇒ **誤攔一切含中文之 `Bash` 命令**（＝ 條件 `②` 所稱之**誤攔**情形）。
**修**：改自 `sys.stdin.buffer` 取**位元組**後顯式以 UTF-8 解碼。
**修後**：含 CJK 而不含 `⟨INTRO⟩` 之命令**通過** ✅。

### 一之 `c`　🩸 **第二個真缺陷**：`stdout` 之 deny JSON **覆蓋** `exit 2` ⇒ **回落放行**

修 `b` 後，含 `⟨INTRO⟩` 之命令**仍未被攔**。

🔒 **取事件之實際形狀為證（⛔ 推測）**——暫加診斷傾印，得活體事件（節錄·**已去識別**）：

```
"hook_event_name":"PreToolUse","tool_name":"Bash",
"tool_input":{"command":"…⟨INTRO⟩…","description":"…"}
```

⇒ `tool_name` ＝ `Bash`、`tool_input.command` **確含 `⟨INTRO⟩`** ⇒ **事件形狀無誤**。

🔒 **隔離實驗**（以**該筆活體事件之原文**直餵 guard）：

| 端 | 結果 |
|---|---|
| `rc` | **2**（期望 2）✅ |
| `stderr` | `🔴 [wg9237_heredoc_guard] 已阻斷：Bash 命令含 heredoc 引入符` ／ `命中樣式 ＝ H1 …（偏移 9）` |
| `stdout` | `{"hookSpecificOutput": {…, "permissionDecision": "deny", …}}` |

⇒ 🔒 **guard 側正確 ⇒ 問題在 harness 之阻斷契約**。

🔒 **與已知<u>成功</u>攔截案之唯一差**：`b` 之 CJK 案走「**僅 `stderr` ＋ `exit 2`**」（**確被攔**）；
本案另寫了 **`stdout` 之 deny JSON**。
⇒ **假說**：`stdout` 之 JSON **覆蓋** `exit 2`，而其驗證未過 ⇒ **回落放行**。
**實驗**：移除 `stdout` 之 deny JSON、只留 `stderr` ＋ `exit 2`。
