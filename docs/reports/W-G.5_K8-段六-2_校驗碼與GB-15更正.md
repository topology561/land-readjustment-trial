## 一、🔴 必修：PROVENANCE 校驗碼對不上入庫產物

### 1-a 實測（本批自算）

| | 來源檔 | **入庫 blob（段六首版 `28cbf51`）** |
|---|---|---|
| bytes | 88,405 | **76,081** |
| CR 數 | 12,324 | **0** |
| md5 | `dfaf3daf1f6aaaa4e5dec8acdbb21f48` | **`7f56ef4e46d5f414d9d80367095eb6ab`** |

**成因**：本倉 `core.autocrlf=true` 且**原無 `.gitattributes`**
⇒ git 以**啟發法**視 `.dxf` 為文字檔，入庫時做 **CRLF→LF 正規化**。
**內容未損**（轉回 CRLF 與原檔逐 byte 相同、幾何集合逐鍵一致），**但校驗碼失準**。

⚠️ 同倉 `data/V6.dxf` **未**被正規化（blob 仍含 CR 12,308、md5 與工作區相同）
⇒ **兩檔待遇不一致**——**啟發法非契約**，此不一致本身即隱患。

### 1-b `.gitattributes`：**選 `-text`，不選 `binary`**

```
*.dxf -text
*.dwg -text
```

| | `-text` | `binary` |
|---|---|---|
| 語意 | **僅**關閉行尾正規化 | git 內建巨集 ＝ **`-diff -merge -text`** |
| 行尾 | ✅ 凍結逐 byte | ✅ 凍結逐 byte |
| 文字 diff | **保留** | 關閉 |
| 文字 merge | 保留 | 關閉 |

**選定理由**：`-text` **恰好對症**（缺陷即行尾正規化）。
本倉 DXF 係**受審查資產**——`git diff` 能逐行指出「只有 3 個端點座標變動」，
段六即賴此診斷；而 `-merge` 會改變衝突解析行為，係**逾越本次所需之副作用**。
⇒ **取最小且對症者。**

## 三、🔴 GB-15 之歸因更正（**本批最重要之一項·亦即 KL 之提問**）

### 3-a 問題

段六首版將「R1 左 `−0.166151m`／R3 右 `−0.059879m`」登記為**圖面落差**
（GB-15：「街廓多邊形之前緣側邊界並不落在 FRONT_LINE 上」），
並據以宣稱「修圖只解決 R4 一角，R1／R3 仍待處置」。

**該歸因錯誤。**

### 3-b 實測（新增之【5b】判準）

**真正之圖面落差** ＝ **各街廓多邊形本身**之頂點對 `FRONT_LINE` 之最大垂距。
逐街廓（**舊圖 `V6`**·前緣側 max t）：

| R1 | R2 | R3 | **R4** | R5 | R6 |
|---|---|---|---|---|---|
| `−0.000013` | `0.000000` | `0.000000` | **`+0.014826`** | `0.000000` | `0.000000` |

⇒ **全六街廓之中只有 R4 曾有圖面落差；R1／R3 從來就沒有**（13µm 以內）。
`V6_1` 修後**全區 ≤ `7.6e-6 m`**。

### 3-c 那「`−0.166m`／`−0.060m`」是什麼？

是**街角規定範圍多邊形自身**於**退縮 0m** 之前緣側極值。
退縮 0m 時該範圍很窄，**整個落在截角區內**，其前緣側極值遂落在**截角邊**上
——**與圖面畫得準不準無關**。

**兩項獨立實證**：

1. 該值與「**不扣截角**」之值**逐格相同** ⇒ **非**扣截角所致；
2. 同一街角於**退縮 3.5m** 時回到 `−0.000013`（R1 左）／`−0.000001`（R3 右）
   ⇒ 範圍夠大、已越過截角。

⇒ **R4（圖面）與 R1／R3（0m 範圍落在截角內）非同源、非同類問題。**
